# Simple Git CMS

[English](README.md) · [简体中文](README.zh-CN.md) · **日本語**

![Simple Git CMS エディター：説明付きの画像がある記事を編集しているところ](docs/screenshot.png)

**[ブラウザーで試す](https://simple-git-cms.azq1994.com/demo/)** — エディターそのものです。GitHub の代わりに Service Worker が応答します。ログインは不要。

**GitHub リポジトリをバックエンドにする**静的サイト用のコンテンツエディターです。記事はリポジトリ内の
Markdown ファイルで、エディター自体はただの静的ページ。書く人のブラウザから GitHub API を直接読み書き
するので、**自前のサーバーもデータベースも要りません**。

Astro や Hugo のような静的サイトに向いています。記事を書いて画像を入れて公開する——その裏側は
git のコミット 1 回で、あとは GitHub Actions などの CI がビルドして公開します。

## できること

- **そのまま見たまま編集**（TipTap）して、きれいな Markdown で保存。既存の記事を開いて保存し直しても
  ファイルは変わりません
- **画像**：貼り付け・ドロップ・複数選択に対応し、ブラウザ内で webp に圧縮。切り抜き、回転、説明、
  横並び、差し替えができます
- **自分で定義するブロック**：動画、お知らせの枠、セルを結合した表——サイトがすでに描けるもの。
  `config.json` にタグを書けば「挿入」メニューに並び、それぞれに合った編集のしかたが付きます：
  小さなフォーム、表のエディター、あるいはその要素の HTML そのもの
- **コード**：インラインの `コード` とフェンスのコードブロック（言語の指定も保たれます）。
  エディターが文字に対してする他の処理は中身に触れません
- **表**：行と列の追加・削除、列ごとの左 / 中央 / 右揃え。ファイルには桁の揃った GFM の表として
  書き出されます。それ以上のもの（1 つのセルが 2 列にまたがるなど）は HTML の表で、サイトが
  自分で定義するブロックになります
- **添付ファイル**：PDF などはそのまま（圧縮せずに）リポジトリに入り、元のファイル名のリンクとして
  本文に挿入されます。サイズの上限は設定できます
- **知らないものを黙って捨てません**：エディターにボタンのないもの——埋め込み、残っている `<div>`、
  サイト側で展開されるコンポーネント——はソースを直接編集できる HTML ブロックとして表示され、
  保存時はそのまま書き戻されます
- **アイキャッチ画像**：記事にすでにある画像から選ぶか、新しくアップロードし、記事の情報欄で
  差し替え・切り抜き・削除ができます。指定した frontmatter の項目に書き込まれ、一覧のサムネイルや
  SNS 用の画像に使うあれです
- **記事**：タイトル、日付、タグ、要約、下書き / 公開 / 下書きに戻す / 下書きの削除。開いている
  記事はアドレスバーに入るので、再読み込みしても元の記事に戻り、その URL はログインできる人への
  リンクにもなります
- **保存**：記事と新しい画像をまとめて 1 つのコミットに。開いている間に他の人が同じ記事を変更していた
  場合は、相手の版か自分の版かを選べます
- **履歴**：記事を変更したコミットごとに、その時点の版を見られます。サイトのプレビューでも表示できます。
  版に戻すとエディターに読み込まれ、保存すると「どの版から復元したか」を書いた新しいコミットになります。
  公開・下書きの状態はそのままです
- **書きかけは失われません**：コミットしていないものは入力しながらブラウザーに控えが残り（アップロード
  前の画像も含めて）、クラッシュ・タブを閉じた・再読み込みのあとに戻すか尋ねます
- **プレビュー**：サイト自身のレイアウトで（パソコン / スマートフォン幅）、未保存の内容や画像も含めて
  確認できます
- **デプロイ**：下書きの保存には `[skip ci]` が付くのでビルドは走りません。公開後はヘッダーに
  GitHub Actions の進行状況が出ます
- **実行ボタン**（任意）：指定した GitHub Actions の workflow をワンクリックで実行。たとえばエディターのある
  テストサイトから本番サイトへの公開。本番サイトにはエディターを置かずに済みます
- **ログイン**：GitHub App でのログイン（全画面リダイレクト方式なのでスマートフォンでも使えます。
  トークンは App を入れたリポジトリにしか届かず、期限切れは自動で更新）、または Fine-grained
  アクセストークン
- **権限はリポジトリの権限そのまま**。push できる人が編集でき、誰が何を変えたかは git の履歴に残ります
- **画面は英語・简体中文・日本語**に対応、その場で切り替えられます
- **ライト / ダーク**：システムに合わせるか、自分で選ぶか

## サイトに組み込む

### 1. ビルドしてインストール

サイトのリポジトリで：

```bash
npm install --save-dev simple-git-cms
npx simple-git-cms install public/editor   # サイトの静的ディレクトリ。URL は /editor/ になります
```

インストールで上書きされるのはエディター自身のファイルだけで、インストール先の `config.json` と
`logo.png` はそのまま残ります。更新するときは `npm update simple-git-cms` してから、もう一度
インストールしてください。

パッケージに入っているのはビルド済みのエディターと、サイトが読み込む 2 つのファイル（後述）です。
このリポジトリを clone して使う場合は `npm install`、`npm run build` のあと
`node scripts/install.mjs ../my-site/public/editor` です。

### 2. `config.json` を書く

エディターと同じディレクトリに、`config.example.json` を参考にして置きます。

| 項目 | 説明 |
|---|---|
| `title` / `siteName` / `logo` | 画面に出る名前とロゴ |
| `lang` | 画面の最初の言語：`en` / `zh` / `ja`。省略するとブラウザの言語に従います。本人がメニューで選んだ言語が優先されます |
| `repo` / `branch` | コンテンツのあるリポジトリ |
| `siteUrl` | サイトのアドレス。「サイトで見る」に使うほか、エディターがサイトと別ドメインにあるときは画像の読み込みにも使います |
| `timeZone` | 日付の表示、画像フォルダー、新しい記事の番号に使うタイムゾーン |
| `auth.base` | ログイン中継のアドレス |
| `collection.dir` | 記事のディレクトリ（リポジトリ内のパス）。記事 1 本につき `<id>.md` が 1 つ |
| `collection.url` | 記事の URL。`{id}` が置き換わります |
| `collection.imageField` | アイキャッチ画像を書き込む frontmatter の項目名（例：`image`）。省くとアイキャッチ画像の欄は出ません |
| `media.dir` / `media.url` | 画像のリポジトリ内ディレクトリ / サイト上のパス。新しい画像は `<日付>/` の下に入ります |
| `media.maxWidth` / `media.quality` | アップロード時に圧縮する最大幅と webp の品質 |
| `media.maxFileMB` | 添付ファイルの上限サイズ（MB、既定は 20。理由は下記） |
| `blocks` | このサイトが自分で定義するブロック。[自分でブロックを定義する](#自分でブロックを定義する)を参照 |
| `preview.url` | サイト側のプレビューページ（下の手順 4）。空なら「プレビュー」ボタンは出ません |
| `deploy.skipCiForDrafts` | 下書きの保存に `[skip ci]` を付ける（既定は true） |
| `actions` | サイドバーの実行ボタン。それぞれ `workflow_dispatch` トリガーのある workflow を実行し、進行状況を表示します。各項目：`label`（ボタンの文字、必須）、`workflow`（ファイル名。例：`release.yml`、必須）、`ref`（ブランチ、既定は `branch`）、`inputs`（workflow に毎回渡す値）、`confirm`（確認ダイアログの文言）、`url`（成功後に表示するリンク）。GitHub App に **Actions: Read and write** が必要です（[auth/README.ja.md](auth/README.ja.md)） |

**`media.maxFileMB` をどこまで上げられるか。** ファイルはログイン中継を通りません——ブラウザーが
GitHub へ直接送ります——ので、効いてくるのはサイトをどこに公開しているかと、GitHub が何を置かせて
くれるかです。Cloudflare Pages と Cloudflare Workers の静的アセットは、どのプランでも 1 ファイル
25 MiB までです。既定の 20 はその下に取った余裕です。GitHub は 100MB を超えるファイルを拒否し、
50MB を超えると警告します。しかもアップロードは base64 なので、リクエスト自体はさらに 3 分の 1 大きく
なります。もう一つ知っておきたいのは、添付ファイルは版ごとにリポジトリの履歴へ残り続けることです。
毎年差し替えるパンフレットはオブジェクトストレージに置いて記事からリンクするほうが向いています。
数 MB のものを一度きり、というのがこの機能の用途です。

`config.schema.json` も隣に入るので、JSON Schema を解釈するエディターなら項目を補完し、打ち間違い
をその場で指摘します。エディター自身も起動時にこのファイルを検査し、問題を一度にすべて並べます。
知らない設定も含めて——以前はそれが黙って無視されていました。

### 3. ログイン中継を置く

[auth/README.ja.md](auth/README.ja.md) を参照してください。手順は Cloudflare Workers で書いていますが、
中継は標準の Web API しか使っていないので、Deno Deploy・Vercel・Netlify・Bun・普通の Node サーバーでも
そのまま動きます。

### 4. サイト側

画像の説明と横並びの表示は [integrations/astro/README.ja.md](integrations/astro/README.ja.md) を参照。

プレビューを使うには、記事ページと同じレイアウトのページをサイトに 1 枚足して、
`simple-git-cms/preview-client` の `connectPreview`（[ソース](integrations/preview-client.js)）を読み込み、
`connectPreview(article => …)` の中でタイトル・日付・タグ・`article.html` をページに入れてください。
エディターは本文をサイトと同じ流れ（remark-gfm、smartypants、rehype-figures）で HTML に変換して送るので、
プレビューページは表示するだけで済みます。

記事ページにそれ以外のものを出している場合も、プレビューに届きます。`article.image` はカバー画像
（未設定のとき、または `imageField` を設定していないときは `null`）で、アップロード前でもそのまま
`<img src>` に入れられます。`article.fields` はそれ以外のフロントマターの項目（著者・カテゴリー・
イベントの日付など）を、ファイルに書かれたとおりに持っています。

```js
connectPreview((article) => {
  cover.hidden = !article.image;
  if (article.image) cover.src = article.image;
  author.textContent = article.fields.author ?? '';
  // …タイトル・日付・タグ・article.html は上のとおり
});
```

### 5. 書く人を追加する

GitHub アカウントと、リポジトリの共同作業者（Write）権限が必要です。GitHub App もそのリポジトリに
インストールしておきます。

## 記事の形式

```markdown
---
title: "タイトル"
description: "要約（省略可。省略すると本文の冒頭から作られます）"
date: 2026-10-21T03:00:00.000Z
tags: ["タグ1", "タグ2"]
draft: true            # 下書きのときだけ付きます
---

本文（Markdown）。![](/uploads/20261021/abc.webp "画像の説明")
```

frontmatter のうちエディターが知らない項目はそのまま残ります。新しい記事のファイル名（= id）は、
作成したときの「年月日時分」です。

本文のうちエディターに対応するノードがないもの——`<iframe>`、`<div>`、HTML コメント、サイト側で
展開されるコンポーネント——は生の HTML のかたまりとして保持され、保存時はそのまま書き戻されます。
エディターではソースの入った箱として表示されるので、ツールバーにないものを記事に入れる手段にも
なります。本文にマークアップを貼り付けたときも同じです。動画サービスからコピーした埋め込みコードは、
ファイルから読んだときと同じカードか箱になります——タグの文字列でもなければ、何も残らない（ノードの
ないタグをエディターはふつう捨てます）のでもありません。箱の中のものはすべてその箱のものなので編集でき、そのぶん出入りも箱自身が持っています——矢印キーで
たどり着き、Enter で入り、Esc で出ます。隅の × か、空にしたうえでの Backspace で取り除けます。

Markdown はその箱どうしを別々のものとして扱います——HTML のかたまりは最初の空行で終わり、その先は
見ません——が、できあがるページはそうではありません。`<div style="color: red">aaaaaa` が閉じられて
いなければ、以降のすべて、記事の外のページ部分まで中に入ってしまいます。そこでエディターは、本文の
HTML を箱をまたぎ、空行をまたぎ、文章の中まで通してひとつながりに読みます——本文に直接書いたタグも
HTML だからです。閉じられないまま開いたものはその場に印が付きます。箱なら箱、文章ならその数文字に。
保存の前にはタグと行を伝えます。「保存」でも「更新」でも同じです。拒否ではなく警告です——あなたのマークアップですし、書いている
途中かもしれないので。

本文の表は普通の GFM の表です：見出し行が 1 行、1 セルに 1 行、セルの結合はなし。手で書いた表は
最初の保存で一度だけ桁を揃え直し（列幅に合わせて空白を入れ、コロンも列幅に従います）、そのあとの
保存では変わりません。サイト側に入れるものはありません。Astro などは最初から remark-gfm を通して
いるので、必要なのは表のスタイルだけです。

パイプの表に書けないことは HTML で書きます——`<table>` は Markdown をそのまま通ります。それを表と
して編集するかソースとして扱うかは、サイトが決めます：`blocks` に
`{ "tag": "table", "edit": "table" }`（下記）を足すと「挿入」メニューに高度な表が増え、記事に
すでにある HTML の表も編集できる表になり、セルの結合 / 解除のボタンが出ます。足さなければ HTML の
表はソースの箱——エディターが知らされていない他のタグと同じ扱いです。どちらでも失われるものは
ありません。なお、エディターがそのまま書き戻せないもの（独自の class など）が入っている HTML の
表は、このブロックを定義してもソースの箱のままです。

## 開発

プルリクエスト歓迎です。必要なことは [CONTRIBUTING.md](CONTRIBUTING.md) にあります。セキュリティの問題は
issue ではなく [SECURITY.md](SECURITY.md) の方法で知らせてください。

```bash
npm install
npm test
npm run dev     # ビルドして http://localhost:4173 でエディターを開きます
```

`npm run dev` は初回に `dev.config.json`（gitignore 済み）をリポジトリのルートに作ります。ビルドのたびに
`dist/` へコピーされるので、再ビルドしても残ります。

**編集対象は GitHub ではなく、このマシンのファイルです。** `npm run dev ../my-site` と書くと、そのチェック
アウトがエディタの後ろに入ります。サインインは不要、一覧はディスク上の `collection.dir` から読み、保存は
記事と画像を書き出してそこにコミットします——1 つのコミット、メッセージはエディタが使うものと同じ、触れた
パスだけ。ステージしてあった他の変更はそのまま残ります。push はご自分で：エディタはファイルを書くもので、
何を出すかを決めるのは git のまま、という考えです。パスを省くとエディタ自身のリポジトリを編集します。
サイトの中にインストールした場合がこの形です。

マージやリベースの途中のリポジトリには、書き込みはしてもコミットはせず、エディタがそう表示します。開いて
いる間にファイルがディスク上で変わっていた場合（自分のエディタで直した、など）は保存を止めて両方の版を
見せます。GitHub 上で誰かが変えたときと同じ動きです。

localhost で `localStorage['simple-git-cms-api']` を設定すると、GitHub API をローカルのプロキシ経由に
できます。ブラウザテストが使っているのはこれで、ファイル編集より優先されます。

依存を足したり変えたりしたら `npm run licenses` を実行し直してください。実際にバンドルされた
パッケージから [THIRD-PARTY-NOTICES.md](THIRD-PARTY-NOTICES.md) を作り直します。CI でも確認しています。

### 翻訳

言語ごとに `src/i18n/` の下の 1 ファイル（`en.js`、`zh.js`、`ja.js`）に文字列が並んでいます。
追加するときは `en.js` をコピーして訳し、`src/i18n/index.js` の `locales` に足してください。
キーの不足・余り・空文字、`{プレースホルダー}` が英語と合わない場合はテストが落ちるので、
訳し残したまま出ることはありません。

## 自分でブロックを定義する

ここでの Markdown は Markdown ＋ HTML です。`<table>`、`<iframe>`、ビルドがもともと素通しする
ものはそのまま書けます。知らないタグをエディターはソースの箱として表示しますが、そのタグを
`config.json` に書くと「挿入」メニューに並び、それぞれに合った編集のしかたが付きます。

```json
"blocks": [
  {
    "tag": "YouTube",
    "label": "YouTube",
    "preview": "https://i.ytimg.com/vi/{id}/hqdefault.jpg",
    "fields": [{ "name": "id", "label": "動画 ID", "placeholder": "dQw4w9WgXcQ" }]
  },
  {
    "tag": "aside",
    "name": "notice",
    "label": "お知らせ枠",
    "attrs": { "class": "notice" },
    "fields": [{ "name": "text", "from": "content", "multiline": true }]
  },
  {
    "tag": "table",
    "label": "高度な表",
    "edit": "table"
  }
]
```

要素の属性がそのままフォームの項目になります。エディター自身は YouTube が何かを知りません。
どの定義も名乗り出なかったタグは、これまでどおり生の HTML としてソースで編集します。

| 項目 | 役割 |
|---|---|
| `tag` | 要素名。`YouTube` や `aside` など |
| `label` | 「挿入」メニューに出る文字。省略するとタグ名 |
| `name` | 同じタグの定義が 2 つあるときだけ必要 |
| `edit` | このブロックの編集のしかた：`fields`（既定）は小さなフォーム、`table` は表のエディター（行・列・揃え・セルの結合）、`source` はその要素の HTML を、このブロックの名前を付けた箱で編集します |
| `attrs` | このブロックであるために必要で、かつ常に書き戻される属性。`<aside class="notice">` を他の `<aside>` と区別するのがこれです |
| `starts` | 値がこれで始まる要素だけがこのブロックになります。`<iframe>` の種類を見分けるのがこれです。条件であって、`attrs` と違い書き戻されることはありません |
| `fields` | 人が入力する属性。`from: "content"` にするとタグの間の内容になり、`multiline` で複数行になります |
| `preview` | 任意。エディターに出すプレビュー画像で、`{項目名}` が使えます。別サイトの画像なら下のポリシーの `img-src` に足してください |

ファイルにあって `fields` に書かれていない属性も、保持したうえで項目として出します。手で直すしか
ないものは作りません——ただし畳んで、一行の裏に入れてあります。動画サービスが渡してくる埋め込み
コードは属性が 8 つあり、そのうち 7 つは毎回同じだからです。邪魔にはしない、隠しもしない。フォームに収まらないこと（対応する項目のない内容）を言っている要素は、
取りこぼす形で読み込むより、生の HTML のままにします。

宣言したタグは、ファイルの中で空行をまたいで書かれていても 1 つの要素として読みます。Markdown では
HTML のかたまりは最初の空行で終わるので、段落が 2 つ入ったお知らせ枠は、開始タグと段落と、本文に
取り残された `</aside>` になってしまうからです。

エディター自身は、動画も地図もツイートも知りません。記事がいま埋め込んでいるものがそのままタグで、
そのタグを config.json に書けばブロックになります——サイト独自のコンポーネントがあるならその名前、
本文に埋め込みコードが入っているなら `iframe` です。

タグだけでは広すぎることがよくあります。`<iframe>` は動画かもしれず、地図かもしれず、フォームかも
しれません。どれなのかはアドレスに出ます。そのための `starts` です——指定した文字で値が始まる要素
だけをその定義が引き受け、外れたものは次の定義へ、どれも引き受けなければ生の HTML のままです。

```json
{
  "tag": "iframe",
  "name": "video",
  "label": "動画",
  "starts": { "src": "https://www.youtube.com/embed/" },
  "fields": [{ "name": "src", "label": "埋め込みアドレス" }]
}
```

要素はファイルに書かれていたとおりの形で戻ります。自己終了か対か、属性は何があったか——
`<iframe …>` は HTML なので閉じタグを保ち、`<YouTube … />` はコンポーネントなのでスラッシュを
保ちます。

フォームが合わないものもあるので `edit` があります：`table` は `<table>` に表のエディターを与え、
`source` は名前を付ける価値はあってもフォームにするほどではないタグ向けです——中身は同じ HTML の
箱で、付けた名前が出て、挿入したときには要素がすでに書かれています。

サイト側での表示は、これまでどおりサイトの仕事です。エディターのプレビューはブラウザーで Markdown
を変換しているので、サイトが展開するタグはそこには出ません。

## エディターを締めておく

トークンは `localStorage` にあるので、エディターのアドレスでスクリプトを実行できるものはそれを
読めます。そしてそのトークンにはリポジトリへの書き込み権限があります。Content-Security-Policy
ヘッダーはそれを止めるためのものです。エディター自身のファイル以外は、何も実行されません。

<!-- csp:begin -->
```http
Content-Security-Policy:
  default-src 'none';
  script-src 'self';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: blob: https://avatars.githubusercontent.com;
  connect-src 'self' https://api.github.com https://cms-auth.example.com;
  frame-src 'self';
  base-uri 'none'; form-action 'none'; frame-ancestors 'none'
```
<!-- csp:end -->

実際に置くときは 1 行です。ここで折ってあるのは読みやすさのためです。
`https://cms-auth.example.com` は自分の中継に置き換えてください。エディターとサイトのドメインが
違う場合は、サイトのアドレスを `img-src` と `frame-src` にも足します。

| ディレクティブ | 理由 |
|---|---|
| `default-src 'none'` | まず全部断り、そこから 1 行ずつ開けます |
| `script-src 'self'` | 肝心なのはこの行。動くのはエディター自身のファイルだけで、差し込まれた `<script>` はインラインでもそうでなくても何もしません |
| `style-src … 'unsafe-inline'` | 避けられません。TipTap と切り抜きが `style` 属性を書きます。スクリプトの同じ緩和よりずっと弱く、CSS から `localStorage` は読めません |
| `img-src … avatars.githubusercontent.com` | ログインしている人のアバターは GitHub から来ます |
| `connect-src` | エディターが話してよいのは GitHub API と自分の中継だけ |
| `frame-src 'self'` | プレビューの iframe に入るのは自分のサイトです |
| `frame-ancestors 'none'` | 誰もエディターを自分のページに埋め込めません |

`'unsafe-eval'` も、スクリプトの `'unsafe-inline'` も要りません。ページにインラインスクリプトは
なく、バンドルのどこにも `eval` はないからです。`npm run test:e2e` はこのポリシーのもとで
エディターを配信するので、何かがこれを壊したら CI が先に気づきます。

エディターを `/editor/` に入れた場合、置き場所は：

```
# Cloudflare Pages、Cloudflare Workers の静的アセット、Netlify —— サイト直下の _headers
/editor/*
  Content-Security-Policy: default-src 'none'; script-src 'self'; …
  X-Content-Type-Options: nosniff
  Referrer-Policy: strict-origin-when-cross-origin
```

nginx は `location /editor/` の中に `add_header Content-Security-Policy "…" always;`。Apache は
`<Location "/editor/">` の中に `Header always set Content-Security-Policy "…"`。Vercel は
`vercel.json` の `headers`。ヘッダーがどうしても設定できないときは、エディターの `index.html` に
`<meta http-equiv>` を置けば大半は効きます。ただし `frame-ancestors` は meta では無視されます。

**できないこと。** 書き換えられた `app.js` は止められませんし、サーバーの中身を変えられる人も、
ブラウザー拡張も止められません。トークンは `localStorage` にあるままで、これはそこへ至る普通の
道を塞ぐだけです。

## わかっている制限

- 書く人に GitHub アカウントが必要です（なしで済ませるなら、GitHub App としてコミットする
  自前のログインを別に用意することになります）
- 1 サイトにつき記事のまとまりは 1 つで、項目は上記のものに固定です
- プレビューはブラウザ内で Markdown を変換するので、サイト側で別途足した Markdown プラグインは
  反映されません
- 外部の画像アドレス（他のページから貼り付けたもの）は保存時に弾かれます。ダウンロードして
  アップロードし直してください
- GitHub のトークンは `localStorage` に入ります。バックエンドのないエディターでは普通の割り切りですが、
  エディターと同じオリジンにスクリプトを差し込める人はトークンを読めます。自分で管理している
  ドメインに置き、素性の分からないスクリプトを同じドメインに置かず、[エディターを締めておく](#エディターを締めておく)
  のポリシーを付けてください
